# Console management integration

The opt-in `/v1` HTTP API is independent of RustDesk's client protocol ports and is served by hbbs only. Set `RD_MANAGEMENT_BIND` to a private socket address, `RD_MANAGEMENT_TOKEN` to an independent random Bearer credential of at least 32 characters, and `RD_MANAGEMENT_DIR` to a persistent directory for management state. Do not publish this listener to the client-facing network.

hbbs exposes `GET /v1/status`, `GET /v1/config`, `PUT /v1/config`, `GET /v1/logs`, `GET /v1/peers`, `GET/PUT /v1/bans`, `POST /v1/restart`, `GET /v1/events` (SSE), `GET /v1/relays`, `GET /v1/relays/:id/sessions`, `DELETE /v1/relays/:id/sessions/:uuid`, `GET/PUT /v1/relays/:id/config`, `GET /v1/relays/:id/logs`, `POST /v1/relays/:id/restart` and `GET /v1/control` (WebSocket upgrade). hbbr exposes no HTTP listener; it is managed entirely through the hbbs control channel. All endpoints require authorization. API version is 1. Session closure is asynchronous (`202`, `state: closing`). IP bans check both relay endpoints. Reported target IDs are not authenticated source identities.

Relay aggregation: when `RD_HBBS_API_URL` is set on hbbr, it opens an outbound WebSocket to the hbbs management API (`/v1/control`), registers with its relay identity and reports heartbeats, session lifecycle events and session snapshots. hbbs fans the active ban policy out to every registered relay (on update and on registration), aggregates relay sessions behind `GET /v1/relays/:id/sessions`, forwards disconnect requests through `DELETE /v1/relays/:id/sessions/:uuid`, proxies relay-scoped management requests (`GET/PUT /v1/relays/:id/config`, `GET /v1/relays/:id/logs`, `POST /v1/relays/:id/restart`) over the control channel using request ids and HTTP-equivalent responses (a relay that stays silent fails the proxy request after 10 seconds), and folds each relay address reported at registration into the live relay server list (static `relay-servers` plus registered relays; dynamic `relay-servers` updates replace the static baseline and keep the registered addresses). hbbr identity comes from `RD_RELAY_ID` (or `HOSTNAME`); `RD_RELAY_ADDRESS` optionally advertises the address clients use to reach the relay and is folded into the live relay server list only when set — the relay id (often a container hostname) is never broadcast as an address. A re-registering relay replaces its previous connection, and registrations silent for 45 seconds are dropped. `GET /v1/events` streams aggregated events (`peer_online`, `peer_offline`, `session_opened`, `session_closed`, `relay_registered`, `relay_disconnected`, `bans_replaced`) as server-sent events with a 15 second keep-alive.

Set `RD_HBBS_API_URL` to the management origin or the full control WebSocket URL, and set the same `RD_MANAGEMENT_TOKEN` on hbbr and hbbs:

| Input | Control WebSocket URL |
| --- | --- |
| `http://hbbs:21120` | `ws://hbbs:21120/v1/control` |
| `ws://hbbs:21120/v1/control` | `ws://hbbs:21120/v1/control` |
| `hbbs:21120` | `ws://hbbs:21120/v1/control` |
| `[::1]:21120` | `ws://[::1]:21120/v1/control` |
| `https://management.example.com` | `wss://management.example.com/v1/control` |
| `wss://management.example.com/proxy/v1/control/` | `wss://management.example.com/proxy/v1/control` |

Surrounding whitespace is trimmed. An empty or root path becomes `/v1/control`; an explicit non-root path is retained with trailing slashes removed, for reverse proxies that expose the control endpoint at another path. HTTP and HTTPS schemes select WebSocket and TLS WebSocket respectively; an address without a scheme uses WebSocket. IPv6 addresses must be enclosed in brackets. HTTPS/WSS requires a TLS reverse proxy in front of the hbbs HTTP listener. The WebSocket client verifies the certificate chain and hostname using its bundled public trust roots, including in the scratch image; self-signed/private-CA certificates are not trusted by this client.

Invalid URLs, unsupported schemes, embedded credentials, query strings and fragments are rejected at hbbr startup, before the reconnect task is created. Supply the Bearer credential through `RD_MANAGEMENT_TOKEN`, never in the URL. A token shorter than 32 characters or invalid as an HTTP header also fails startup. Diagnostics identify the setting and reason without printing its value. Leave `RD_HBBS_API_URL` unset or empty to disable aggregation. Temporary connection failures still retry with exponential backoff from 1 to 60 seconds.

Files are service-specific: `hbbs-config.json`, `hbbr-config.json`, `hbbs-bans.json`, and `hbbr-bans.json`. Configurations use `{ "values": { "port": "21116" } }`, and policies use `{ "device_ids": [], "ips": [] }`. Saved bans are validated and restored before protocol startup even when `RD_MANAGEMENT_BIND` is empty. Disabling the HTTP listener does not clear admission policy; explicitly replace the bans with empty lists before disabling management if clearing is intended. Ban replacements serialize persistence outside the protocol admission lock and activate only after the write succeeds. Config updates follow the same contract: the merged desired configuration is persisted atomically first, and running state changes only after the write succeeds.

`PUT /v1/config` accepts a partial `{"values": {...}}` merge against the current desired configuration. Schema entries marked `"dynamic": true` take effect immediately without a restart: hbbr applies `downgrade-threshold`, `downgrade-start-check`, `limit-speed`, `total-bandwidth` and `single-bandwidth` live, and hbbs applies `always-use-relay` and `relay-servers` live. The response reports `applied` entries and `pending_restart` entries (with `current` and `pending` values); pending entries take effect on the next restart, when the saved file is loaded before the protocol starts. `GET /v1/config` returns the live effective values, the schema and the current `pending_restart` diff. Secret entries are stored in the clear in the shared directory but are always reported as `__REDACTED__`; submitting the placeholder keeps the stored value unchanged. A missing dynamic handler falls the entry back to restart-required handling.

`GET /v1/logs?tail=N` returns up to 2000 recent in-memory log lines (default 200) captured from the standard log format; it requires no container log access. `GET /v1/relays/:id/logs` proxies the same read for a registered relay.

`POST /v1/restart` (on hbbs and proxied per relay) asks the supervisor to bring the service back: the process exits shortly after the response is flushed (`202`, `state: restarting`), and the persisted configuration including pending-restart entries is applied on the next startup. Relay restarts are fire-and-forget: the relay acknowledges, exits and drops off the control channel, and registers again once it is back.

Managed settings override startup inputs. Schema and validation are provided by `management-schema.json`. The API returns key placeholders, never the private key. It exposes only `id_ed25519.pub` as the public key.

The published `databk/rustdesk-server` image ships hbbs and hbbr with the management API compiled in; deploy each binary as its own container (for example through the Console repository's Compose `server` profile), set `RD_MANAGEMENT_BIND` on hbbs to enable its listener, and set `RD_HBBS_API_URL` on hbbr so it registers on the control channel. The Console repository supplies the combined Compose deployment, permission enforcement, UI, integration workflow and detailed lifecycle documentation in `docs/server-management.md`. Existing binaries remain compatible with deployments that do not enable management.
